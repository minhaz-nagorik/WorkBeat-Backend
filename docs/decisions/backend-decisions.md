# Backend decisions — B1–B21

Rulings this repository made where the plan is silent. Each must agree with WorkBeat Plan v3.5 and
its D-numbers; a disagreement is a defect. Cite them as `B<n>` in specs.

| # | Decision | Why |
|---|---|---|
| B1 | This repository holds `apps/api` (NestJS + Fastify), `packages/shared` (zod contract, constants) and `db/`. The web platform (WorkBeat Admin) is its own repository and consumes `packages/shared` | Plan §6.5 lists one monorepo; the agents already live in their own repositories, and the web platform follows them |
| B2 | Each request runs in one transaction that first sets `app.scope` (`tenant`, `staff`, `system`) and, for `tenant`, `app.company_id`. Row-level security uses them | Plan §6.1 defence in depth; a missed filter returns nothing |
| B3 | Credentials are resolved before a tenant is known through `SECURITY DEFINER` lookups (`auth_device`, `auth_license`, `auth_enrollment_token`, `auth_invitation`, `company_by_host`) that return only what the guard needs | The API never needs a bypass-RLS connection on a request path |
| B4 | Seats used are counted from devices that are neither deactivated nor released, never stored; a trigger refuses the device that would exceed `seat_limit` | D43: seats survive a key reissue and are freed by release; a counter could drift |
| B5 | One global sequence feeds every `policy_version`; a device's version is the greatest of its company's, its employee's and its own | Replaces Plan §6.2 `policy_versions`; the version only grows, so a change in any scope always shows |
| B6 | Licence keys and the uninstall token are stored as SHA-256 for lookup and AES-256-GCM ciphertext (key from the environment) for display. Every other secret is hash-only | The portal must show and copy both (prototype) |
| B7 | Ingested activity records whose time is outside [server now − 8 days, server now + 1 day] are dropped and counted in the response; the batch is still accepted. A screenshot outside the window is refused (422), since its request carries one record. Tamper events are accepted at any age (D24). `ingest_batches` rows are kept 14 days | The agent keeps at most 7 days (D7); a skewed clock must not quarantine a whole batch |
| B8 | `/license/validate` has two steps: without `employee_id` it returns the company and employee list; with `employee_id` it also issues the single-use enrollment token, bound to that employee | D47 makes the employee required and the token carries it |
| B9 | This repository owns the error envelope, the `code` catalog and the payload schemas the agents consume; it answers agent open question Q1 | Plan §3 "Shared types" |
| B10 | `/cron/*` routes authenticate with a shared secret header from the scheduler and run in `system` scope | Plan §3 "Scheduled jobs" |
| B11 | `screenshot_interval_seconds` is one of 0, 600, 1800, 3600, and not more frequent than the company's tier | The agents accept only these values |
| B12 | An employee has at most one manager | Prototype "Manager teams"; the PRD's many-to-many is not used |
| B13 | Data retention is per company, 30, 60 or 90 days (default 90); partitions older than 90 days are dropped, and report, export and screenshot ranges are at most 90 days. Was 1–365 (ranges up to 366 days) until 19 Nov 2026, when the product owner limited it to these three choices (migration 0009) | PRD "Retention and suspension"; partitions cannot be dropped per company |
| B14 | Company status adds `trial` beside `active`, `suspended` and `expired` | Prototype staff area; PRD Starter plan has a 14-day trial |
| B15 | `/cron/cleanup` commits each delete batch in its own short transaction under a per-job advisory transaction lock, and stops at a time budget. Amends B2 for that route only | A retention run can delete millions of rows; one transaction would hold a pooled connection for minutes |
| B16 | `update_package_url` is signed once per release per UTC day and valid to the end of the next day | A fresh signature per request would change the policy ETag every time, so `304` would never happen |
| B17 | `POST /v1/devices/:id/deactivate` with a device key is exempt from `402`: it frees the seat even while the company is suspended or expired | An uninstall must never leave a seat held |
| B18 | `it_admin` can list employees (`id`, `name`, `email`, `department`); it reaches no report, screenshot, pause or monitoring setting | Plan §4.5 gives Employees to Admin and Manager, but IT manages devices and needs to know whom each device is bound to; there is no reassign picker (PRD role table allows it) |
| B19 | Each company has an IANA `timezone` (default `UTC`) that bounds days and weeks in reports, calendars, timesheets, the screenshot day and daily digests | The PRD calendar and Monday-start timesheet need a company day |
| B20 | A device's employee is fixed for the life of its binding; there is no reassign route; enrollment for another employee on a live binding answers `409 DEVICE_ASSIGNED` | D48: records belong to the binding that uploaded them, so one employee's data never reaches another. A trigger refuses `UPDATE devices SET employee_id` (0003) |
| B21 | A released key is accepted on the upload routes (`POST /v1/agents/activity`, `POST /v1/agents/screenshots`, `.../confirm`) for 7 days after `released_at`; every other route answers `401 DEVICE_RELEASED` | D45: the agent uploads what it holds for up to 24 h; 7 days covers a device that was offline at release |
| B22 | No Supabase (16 Nov 2026): self-hosted PostgreSQL; the API owns sign-in. Passwords are scrypt hashes on `users`; a session is an opaque `wbs_…` token stored as SHA-256 in `sessions`, valid 7 days, ended by logout, a password change or reset (other sessions), or removal of the user (0004) | Supabase Auth, Supavisor and Storage are gone; a stored session can be ended at once, which a stateless JWT cannot |
| B23 | Superseded. Removed 16 Nov 2026 by the product owner: staff sign in with password only; Plan v3.5 D41's MFA requirement is waived. Was: staff MFA by TOTP, an `mfa_token` at login and a session only from `POST /v1/auth/mfa/verify` (0005). The MFA columns of `users` and the `mfa_challenges` table from 0005 are unused and may be dropped by a later migration | Product owner decision; staff use the same password sign-in as company users (B22) |
| B24 | Self-service password reset: `POST /v1/auth/password-reset/request` always answers `204` and emails a single-use link valid 30 minutes; confirming it sets the password and ends every session of the user | Without a reset a locked-out last company admin needs WorkBeat support; `204` either way never reveals whether an email has an account |
| B25 | Sign-in is protected by per-IP rate limits, no account lockout: 20 requests a minute per route group (`/v1/auth/*`, `/v1/invitations/*`, `/v1/license/validate`), `429 RATE_LIMITED` with `Retry-After`. Only a proxy on the API host is trusted for `X-Forwarded-For` | A lockout lets anyone lock out a company's admins by guessing; scrypt slows each guess. Trusting any `X-Forwarded-For` would let a client fake its IP |
| B26 | Until an object-storage provider is chosen, screenshots and agent packages are stored on the API host's disk and served through API-signed URLs (`/v1/storage/…`, HMAC with an expiry); the request → `PUT` → confirm flow is the one a bucket's presigned URLs will use | Plan §2.1 assumed Supabase Storage; the agents only ever use the URL they are given, so the provider can change without a contract change. **17 Nov 2026:** screenshots moved to Cloudflare R2 (`R2_*`): `upload_url` and `view_url` are SigV4 presigned R2 URLs (PUT signs `Content-Type: image/jpeg`), confirm checks size with a HEAD; packages stay on disk for now. Local-disk screenshots removed the same day: `R2_*` is required. `download_url` signs `response-content-disposition`/`response-content-type` (Admin round 7) |
| B27 | `/api/v1/…` is served as `/v1/…`, and a licence key is hashed after trimming and upper-casing (`WB-XXXX-XXXX-XXXX-XXXX`) | The agents' specs use a base URL ending in `/api/v1`; IT types the key by hand |
| B28 | Finished company days are summarized by `/cron/usage-summary` (hourly) into `usage_hours`, `usage_apps` and `usage_domains`; reports read summaries for days marked in `usage_days` and raw rows for the rest, and apply categories when read. A late batch rebuilds its employee-day under a per-day advisory lock; a timezone change deletes the company's summaries (product owner, 19 Nov 2026) | Adding up raw rows per request was estimated at 8–20 s for a 90-day report at 100 employees (concern #12); summaries keep the numbers identical and rules still apply to past days |
| B29 | A company admin edits only the idle threshold, the timezone and alert emails in company settings. The company name, data retention, custom domain, collection notice and billing are managed by WorkBeat staff: those routes answer `403 FORBIDDEN` to every company role (`NO_COMPANY_ROLE`), and staff set name and retention with `PATCH /v1/staff/companies/:id` (product owner, 19 Nov 2026) | The product owner keeps these settings with WorkBeat. The screenshot interval stays per employee (D37), within the plan's tier; monitoring settings carry `screenshot_tier`, so the console no longer reads billing |
| B30 | WorkBeat staff set a company's plan (any of starter, growth, enterprise), seat limit, screenshot tier and status (trial, active, suspended, expired) directly: `PATCH /v1/staff/companies/:id/license` and `PATCH /v1/staff/companies/:id`. A tier change raises the company's `policy_version`; the policy caps each employee's interval at the tier (a faster stored value is sent as the tier's interval, the stored value is kept). `expired` sets `licenses.expired_at` (grace from now), leaving it clears it; `trial` needs a future `trial_ends_at` (`trial_days`) (product owner, 19 Nov 2026) | Billing is staff-managed (B29) and Stripe is not built; staff need every commercial setting. Capping at read time means staff never write employee rows (D41) and raising the tier again restores each interval |
| B31 | Tamper is no longer a device status or an employee presence. An unresolved tamper event other than `offline` adds the device badge `open_alert`; the device's status stays `online` or `offline`, and presence is decided from the devices as if there were no alert. `GET /v1/rollout` and `GET /v1/dashboard` count `open_alert` instead of `tamper` (product owner, 19 Nov 2026) | A tamper event is something that happened, not a state the computer or person is in: a laptop with an edited hosts file is still online and its owner still working. The alert stays in the feed until resolved |
